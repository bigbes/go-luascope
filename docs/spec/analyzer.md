# go-luascope: анализатор Lua для Tarantool

Спека на развитие библиотеки `github.com/bigbes/go-luascope` до анализатора с четырьмя
независимыми шагами. Состояние на момент написания: тег `v0.1.0`, коммит `eae0167`.

Документ адресован тому, кто будет это делать, и тому, кто будет это принимать. Расчёты сроков -
для одного инженера, без учёта ревью.

## Слова

Ключевые слова ниже используются в смысле RFC 2119 на русском: **должен**, **не должен**,
**следует**, **не следует**, **может**. Жирным они выделены один раз, здесь; дальше идут как
обычные слова.

- чанк (chunk) - исходник Lua, поданный на разбор целиком.
- узел (node) - элемент синтаксического дерева из пакета `ast`.
- диапазон (range) - полуинтервал байтов `[Start, End)` в исходнике.
- документ (document) - чанк вместе с исходником и таблицами диапазонов.
- находка (finding) - сообщение анализатора о конкретном месте исходника.
- правило (rule) - именованная проверка, порождающая находки.

## Задача

Библиотека умеет разбирать Lua в диалекте LuaJIT для Tarantool, строить дерево, собирать
использованные глобалы и модули и отвергать синтаксические обращения, запрещённые заданной
политикой. Прохождение проверки не означает безопасность выполнения и не исключает косвенного
доступа к запрещённым возможностям. Чего не хватает: командной строки, адресуемых мест в
исходнике и диагностики, кроме ошибок компилятора.

Дальше библиотека нужна трём разным потребителям одновременно: линтеру с проверкой безопасности
выполнения, пониманию кодовой базы (граф вызовов, зависимости, влияние правки) и общему слою,
на котором оба строятся. Разводить три кодовые базы - гарантированно получить три разных
представления Lua, которые расходятся в мелочах. Поэтому ядро одно, а развивается оно шагами.

## Принципы

**Один разбор на исходник.** Разбор дорог: парсер повторяет компилятор LuaJIT, включая
кодогенератор. Повторный проход по дереву ради каждого правила допустим, повторный разбор - нет.

**LuaJIT остаётся эталоном.** Всё, что касается принятия кода, ошибок и номеров строк, сверяется
с настоящим LuaJIT побайтно. Любая новая проверка, которая меняет вердикт о принятии чанка,
недопустима: линтер сообщает о находках, но не превращает годный чанк в негодный.

**Диагностика отдельно от разбора.** Пакет `parser` знает только об ошибках компилятора LuaJIT.
Правила живут снаружи и не влияют на `SyntaxError`.

**Неизвестное сообщается, а не замалчивается.** Если анализатор чего-то не знает, он говорит
"неизвестно" и называет место. Пустой результат и "ничего не нашлось" - разные вещи, и разница
обязана быть видна в API.

**Публичный API не ломается.** `Parse`, `ParseBytes`, `SyntaxError`, `ReadError`, `globals.Usage`,
`Checker.Check` остаются совместимыми. Новое добавляется рядом, а не вместо.

## Чего в спеке нет

Байткода как промежуточного представления для анализа. Кодогенератор в `parser/codegen.go`
остаётся приватным оракулом совместимости: он существует, чтобы отвергать то, что не кодируется
у LuaJIT, и чтобы тесты сравнивали байткод с настоящим LuaJIT. Выводить из него типы значений
нельзя - регистры переиспользуются, а факты принадлежат точкам программы, а не номерам регистров.

Общей системы типов. Lua динамический, `rawget`, метатаблицы и `_ENV`-подобные фокусы в Lua 5.1
делают доказательство типов неразрешимым. Всё, что будет выведено, - это "известно уверенно" или
"неизвестно", без попыток достроить.

Восстановления после синтаксической ошибки. Сейчас `ParseBytes` возвращает `nil` на
`SyntaxError`. Толерантный разбор (для редакторов и для анализа недописанного кода) - отдельная
задача на 2-4 недели, в эту спеку не входит.

Графа вызовов и правил вида `box.space.*`. Для проверок API по схеме нужна версионированная
модель схемы Tarantool, которой пока нет. Синтаксическому графу вызовов она не требуется: он
исключён потому, что не входит в эти четыре шага, а не потому, что ему нужна схема.

## Граница безопасности

Синтаксическое имя глобала не является устойчивой привязкой во время выполнения. `GGET` точно
описывает обращение к глобалу, но не доказывает, какой объект получен: в Lua 5.1 окружения
функций меняются через `setfenv`, а метатаблицы окружения подменяют поиск.

```lua
local execute = os.execute
execute(cmd)          -- вызов не укоренён в os.execute синтаксически
```

Поэтому `allowlist` остаётся инвентарём синтаксических обращений, а успешный проход означает
ровно "по этой политике запрещённых синтаксических обращений не найдено". Формулировка
"безопасно выполнять" недопустима ни в документации, ни в выводе CLI. Ограничения возможностей
на уровне времени выполнения и лимиты ресурсов остаются необходимыми; статический анализ их
дополняет, но не заменяет.

Шаги 1-4 работают только с синтаксисом: ни идентичности объектов во время выполнения, ни
целостности окружений они не предполагают. Профили времени выполнения в этот релиз не входят.

## Шаг 1. Диапазоны исходника

Срок: 5-7 дней.

### Задача

Диагностика без адреса бесполезна: редактору и правке нужны точные байтовые границы, а сегодня
`ast.Pos` несёт только строку и колонку. Колонка есть, конца узла нет.

### Требование

`ast.Pos` не меняется, и интерфейс `ast.Node` не меняется. Оба используются снаружи: `ast.Pos{1, 2}`
через необозначенный литерал ломается от любого нового поля, а внешняя реализация `Node` ломается
от нового метода. Диапазоны живут в отдельном документе, который запрашивается явно.

```go
// Package source хранит исходник и отображение позиции в смещение.
type Range struct {
	Start int // Включительно, байты.
	End   int // Исключительно, байты.
}

type File struct{ /* неэкспортируемые поля */ }

func NewFile(name, text string) *File
func (f *File) Name() string
func (f *File) Text() string
func (f *File) Pos(offset int) (ast.Pos, bool)
func (f *File) Offset(pos ast.Pos) (int, bool)

// Package parser.
type Document struct {
	Chunk  *ast.Chunk
	Source *source.File
	// Неэкспортируемые таблицы диапазонов.
}

func ParseDocument(src []byte, chunk string) (*Document, error)

func (d *Document) Range(node ast.Node) (source.Range, bool)
func (d *Document) LocalRange(loc *ast.Local) (source.Range, bool)
func (d *Document) CommentRange(i int) (source.Range, bool)
```

`ParseDocument` на синтаксической ошибке возвращает `nil` и ту же `*SyntaxError`, что
`ParseBytes`: частичного документа не бывает.

### Что именно означает диапазон

Диапазон обозначает синтаксическую протяжённость узла, а не декодированное значение и не догадку
по соседнему токену. Для всех возвращённых диапазонов выполняется
`0 <= Start <= End <= len(Source.Text())`.

| Что | Диапазон |
|:--|:--|
| `LocalRange` | только идентификатор в объявлении |
| неявный `self` | диапазона нет |
| `ast.String`, играющий роль имени поля или метода | написание идентификатора, без кавычек |
| `ast.String` в роли литерала | литерал целиком, вместе с кавычками |
| `CommentRange` | вместе с `--` и скобками, без завершающего перевода строки |
| пустой `Block` | вырожденный диапазон на позиции блока |
| `ast.Chunk` | весь текст источника |

`ast.Chunk`, `ast.Local`, `ast.Field` и `ast.Comment` не реализуют `ast.Node`, поэтому у них
отдельные методы, а не общий. Для чужого узла или чужой локальной оба метода возвращают `false`.
Индекс комментария вне диапазона тоже даёт `false`, а не панику: тип значения сравним не всегда.

Диапазоны принадлежат снимку разбора. Изменение дерева или подмена `Document.Chunk` и
`Document.Source` делает метаданные недействительными.

`source.File` хранит байты как есть, без нормализации переводов строк и без удаления BOM.
Координаты - те же, что у лексера: номер строки и байтовая колонка от единицы. `Pos` и `Offset`
дают `false` на позиции вне источника и на нулевых значениях; для корректных координат они
взаимно обратны. `ParseDocument` владеет снимком: изменение поданного среза после возврата не
меняет ни `Source.Text()`, ни строки дерева, ни диапазоны. Таблицы диапазонов не должны держать
буферы из пула парсера.

Диапазон узла, у которого его нет, возвращается вторым значением `false`. Выдумывать диапазон из
соседнего токена запрещено: между токенами бывают пробелы и комментарии, а lookahead уже сдвинул
лексер. Неявный `self` в методах не получает диапазона объявления - у него нет имени в исходнике,
и предлагать его к переименованию нельзя.

### Как проверяется

Прогон только старого пути доказывает лишь, что старый путь цел. Поэтому оба оракула -
приёмка-ошибки и байткод - гоняются дважды: с выключенным и с включённым сбором диапазонов.
Между режимами сравниваются дерево, позиции, комментарии и все поля `SyntaxError`. Golden-файлы
остаются неизменными. Отдельно проверяется, что `lastLine` не сдвинулся: байткодовый оракул
печатает инструкции, константы и framesize, но не номера строк инструкций, а оракул глобалов
намеренно допускает расхождение строк, поэтому неизменности golden-файлов недостаточно.

База для замера фиксируется в документе приёмки: коммит `eae0167`, Go 1.x той машины, имя машины,
`BenchmarkParseCorpus` и обе группы `BenchmarkParseFileSize`, отчёт по `B/op` и `allocs/op` для
обоих входов. Корпус для замера берётся тот же, что принимается базовым коммитом, а не тот,
который примет изменённый парсер.

Приёмка: любой реальный узел в принятом корпусе получает корректный ограниченный диапазон;
неявный `self` диапазона не получает; замедление обычного разбора не больше 10% по медиане пяти
прогонов при зафиксированном протоколе, иначе фаза возвращается на доработку.

### Первый риск

Можно ли писать точные концы токенов, не тронув потребление токенов, `lastLine`, lookahead и
ошибки, совместимые с LuaJIT, - вопрос первых двух дней. Читать вместе `parser/lexer.go:127-269`,
`parser/parser.go:190-205`, `parser/parser_expr.go:171-294` и `396-419`,
`parser/parser_stmt.go:559-588` и `704-734`, `parser/codegen.go:338` и `357`: там `emit` читает `lastLine`.

Ответ "да" означает, что фаза продолжается как записано. Ответ "нет" останавливает раскатку
диапазонов: сначала разделяется учёт концов токенов и `lastLine`, и только потом всё остальное.
Править `lastLine` или регенерировать golden-файлы ради метаданных нельзя.

## Шаг 2. Диагностика и командная строка

Срок: 4-5 дней.

### Задача

Библиотека, которую нельзя запустить из терминала, не становится инструментом. Нужна команда,
которая читает файлы, печатает находки и возвращает осмысленный код выхода.

### Требование

```go
// Package diagnostic.
type Diagnostic struct {
	File     string       // Путь, каким его назвал вызывающий.
	Code     string       // "syntax", "allowlist/module", "allowlist/global".
	Severity string       // "error" или "warning".
	Pos      ast.Pos
	Range    *source.Range // nil, если точного диапазона нет.
	Message  string
}

func FromSyntaxError(file string, err *parser.SyntaxError) Diagnostic
func FromViolation(file string, v allowlist.Violation) Diagnostic
```

Синтаксическая ошибка сохраняет `SyntaxError.Line`, включая ноль для ошибок загрузчика байткода,
где никакой строки источника нет. Колонки и диапазона токена она не даёт: `Col == 0`,
`Range == nil`. Выдумывать колонку из сообщения LuaJIT нельзя -
сообщение называет токен, а не его позицию.

`FromViolation` сохраняет позицию и сообщение нарушения, но диапазона не даёт: в
`allowlist.Violation` есть только позиция, имя и вид, провенанса узла там нет. Выделение
исходного идентификатора делает отдельный шаг CLI, который получает документ; выводить диапазон
из форматированной строки пути нельзя.

`ReadError` не превращается в синтаксическую находку: это операционный отказ, и его место - в
кодах выхода, а не в списке находок. Имя файла и номер строки не дублируются в `Message`: они
уже в структуре.

Команда `luascope`:

```
luascope check [--rules rules.json] [--format text|json] [файлы...]
luascope deps  [--format text|json] [файлы...]
```

`check` разбирает каждый файл, проверяет allow-list и печатает находки, упорядоченные по файлу,
строке и колонке. `deps` печатает инвентарь глобалов и `require` без вердикта.

Коды выхода: `0` - находок нет, `1` - находки есть, включая синтаксические, `2` - операционный
отказ или ошибка конфигурации. Смешивать `1` и `2` нельзя: скрипт в CI обязан отличать "код плохой"
от "я не смог посмотреть". Статус `2` главнее `1`: если один файл недоступен, а другой нарушает
политику, команда возвращает `2`.

Читаемые входы обрабатываются, даже если часть входов не открылась. Операционные сообщения идут
в stderr и не портят JSON в stdout. Для `deps` успешный инвентарь даёт `0` независимо от числа
записей; синтаксическая ошибка даёт `1`, операционный отказ - `2`.

Без `--rules` политика считается пустой: запрещено всё, любое обращение - находка. Отсутствующий
или неразобранный файл правил - ошибка конфигурации, код `2`. Неизвестные поля в правилах
отвергаются. Аргумент `-` означает stdin и допускается один раз; повторная подача stdin -
ошибка конфигурации. Каталог в аргументах отвергается с кодом `2`: обход дерева в этом релизе
не делается.

Формат JSON имеет описанную схему, детерминированный порядок и разрешение ничьих: при равных
файле, строке и колонке порядок задаётся кодом находки, затем сообщением.

### Как проверяется

Фикстуры на разрешённые и запрещённые обращения, на динамический `require`, на синтаксическую
ошибку, на битые правила, на отсутствующий файл, на stdin и на несколько файлов. JSON
декодируется и сравнивается с эталоном. Количество находок и сообщения совпадают с тем, что
отдаёт `Checker.Check` на тех же входах.

Приёмка: код выхода различает три случая; в JSON нет выдуманной колонки у синтаксической ошибки;
вывод побайтно стабилен между прогонами.

## Шаг 3. Неиспользуемые локальные

Срок: 4-6 дней.

### Задача

Первое правило, которое приносит пользу без потока управления. Заодно оно проверяет, годится ли
существующая идентичность локальных для реального анализа.

### Требование

```go
// Package locals.
func Unused(chunk *ast.Chunk) []*ast.Local
```

Правило узкое по определению: объявленная локальная или переменная цикла, на которую нет ни
одного чтения нигде в её лексических ссылках. Чтение через замыкание считается использованием.
Параметры, включая неявный `self`, исключены на первом шаге. Имя `_` не сообщается - это
договорённое соглашение, а не находка.

Присваивание без чтения не является чтением: `local x = 1; x = 2` даёт находку про `x`, а
`t[i] = 5` читает `t` и `i` и находок не даёт. Объявление `local function f` входит в правило.
Цель `function f() end` чтением не считается, когда `f` разрешается в локальную.

Возвращается каждое подходящее объявление ровно один раз, в порядке объявления, без повторов
указателей. Синтаксически присутствующее чтение считается всегда, даже в недостижимом коде и в
невызываемом замыкании: достижимость этим шагом не анализируется.

```lua
local f
function f() end            -- f не читается: находка

local function g()
    return g()              -- g читается: находки нет
end

local x
if false then print(x) end  -- x читается: находки нет
```

Диагностика правила: код `locals/unused`, серьёзность `warning`. Правило включено по
умолчанию в `check` и отключается отдельно от allow-list политики.

Про мёртвые присваивания и достижимость правило ничего не утверждает: для них нужен анализ
потока, за который этот шаг не берётся. Удаление объявления не считается безопасной правкой:
инициализатор может иметь побочные эффекты. В этом релизе автоматических правок нет вовсе.

### Как проверяется

Тесты на затенение, на одинаковые имена в разных областях, на рекурсивную локальную функцию, на
захват, на условие `repeat`, на переменные циклов, на параллельное присваивание и на индекс в
цели присваивания. Прогон по всем принятым источникам архивного корпуса - на панику и на
ссылки на несуществующие объявления.

Приёмка: чтение через замыкание отменяет находку; присваивание без чтения находку не отменяет;
`t[i] = 5` не даёт находок про `t` и `i`; каждый возвращённый указатель ссылается на объявление,
которое реально есть в этом чанке.

## Шаг 4. Инвентарь зависимостей

Срок: 3-4 дня.

### Задача

Показать, от чего чанк зависит, не притворяясь, что имена разрешены в файлы.

### Требование

`Checker.CheckUsage(usage *globals.Usage) []Violation` вводится уже в шаге 2: CLI считает
`globals.Analyze` один раз и передаёт результат и в проверку, и в печать. `Check(chunk)` остаётся
обёрткой над `Analyze` и `CheckUsage`. Ни `Check`, ни `CheckUsage` не изменяют и не удерживают
поданный `Usage`; содержимое нарушений, поведение с дубликатами и устойчивый порядок по позиции
сохраняются. `nil` означает пустой вход, а не ошибку.

`globals.Usage` не обобщается в универсальный контейнер результатов: это готовый инвентарь с
проверяемым смыслом, и замена его общим хранилищем грозит двойным учётом обращений и путаницей
чтения с записью. Добавлять поля в `Usage` нельзя по той же причине, по которой нельзя трогать
`ast.Pos`: необозначенные литералы снаружи.

Отдельная модель записи о зависимости вводится рядом:

```go
// Package deps.
type Kind int

const (
	KindRequire Kind = iota + 1
	KindRequireDynamic
	KindRequireValue // require как значение, а не вызов
	KindDofile
	KindLoadfile
)

type Load struct {
	Kind   Kind
	Pos    ast.Pos
	Name   string // Имя модуля, если оно константа.
	Reason string // Почему запись неполна, если неполна.
}

func Collect(chunk *ast.Chunk) []Load
```

`Collect` сохраняет по каждой точке загрузки её вид, позицию и причину неопределённости.
Динамическое имя в `require(...)`, `require` как значение, `dofile` и `loadfile` - разные виды
записи, а не пустое место в списке. Вызов `dofile` отличается от ссылки на `loadfile`:
ссылка на загрузчик не доказывает вызова.

Порядок записей - по позиции. Дубликаты не схлопываются: две загрузки одного модуля в разных
местах - две записи.

### Как проверяется

`Check` и `CheckUsage(Analyze(...))` сравниваются на всех фикстурах allow-list и на принятых
источниках корпуса против независимо записанных ожиданий, а не только друг с другом: общая
регрессия в обоих методах иначе пройдёт проверку. Сравнение касается подмножества находок
allow-list, а не всех находок после шага 3. `Collect` проверяется на своих фикстурах: прямой
`require`, динамическое имя, `require` как значение, `pcall` и `xpcall`, `dofile`, ссылка на
`loadfile` без вызова. Отдельные случаи: прямой `require`,
`require` в скобках, склейка констант, `pcall(require, ...)`, `xpcall(require, ...)` и
затенённый локальный `require`, который зависимостью не является.

Приёмка: динамические `require` остаются видны; затенённый `require` в зависимости не попадает;
ни одна строка вывода не утверждает, что имя модуля разрешено в файл.

## Порядок и зависимости

Шаги идут строго по порядку: шаг 2 печатает диапазоны из шага 1, шаг 3 использует диагностику из
шага 2. Внутри шага 1 первые два дня - проверка риска; если она даёт "нет", остальное не
начинается.

Суммарно 16-22 инженерных дня без учёта внешнего ревью. Оценка условна: она держится, если
двухдневная проверка риска в шаге 1 не потребует перестройки парсера и если публичные контракты
закрыты до начала реализации. Внутрь входит интеграция и приёмочное тестирование. Провал
проверки риска означает переоценку, а не трату остатка бюджета шага на переделку.

Бюджет держится при отказе от правок, подавлений, резолвера модулей, анализа алиасов и профилей
времени выполнения. `CheckUsage` уходит в шаг 2; бюджет шага 4 тратится на модель записей о
зависимости.

## Владение и выпуск

У каждого шага называются исполнитель и принимающий до начала работ; без этого шаг не начинается.
Новые API и команда `luascope` выходят в v0.2.0 с пометкой "added in v0.2.0" в CHANGELOG и в
документации. Совместимость сохраняется для существующих структур, интерфейсов, поведения
парсера, полей и текста ошибок и результатов allow-list. Новые метаданные подключаются только
явно.

Тег v0.2.0 - решение о выпуске, а не требование Go или SemVer: ничего не ломается, но набор
добавлений достаточно велик, чтобы отделить его от v0.1.0.

## Что значит "сделано"

Все четыре шага подключены к описанной команде и публичным API. Независимые проверки проходят:
совместимость, семантика правил, JSON, прогон по корпусу, производительность. Ограничения и
примеры опубликованы. В разделе открытых вопросов не осталось ни одного, который блокирует
выпуск.

## Счётная база

## Открытые вопросы

**Модель схемы Tarantool.** Правила вида `box.space.*` невозможны без версионированного описания
схемы и API, которое поставляет вызывающий. Решить до начала работ над графом вызовов.

**Подавления.** Как пометить намеренное нарушение в исходнике (комментарий-директива) и как это
проверять тестами. Нужно к шагу 2, если `check` пойдёт в CI.

## Что проверяет ревьюер

Что старые оракулы не сдвинулись ни на байт. Что публичный API не сломан. Что в выводе нет
утверждений сильнее, чем может анализ: ни "безопасно", ни "модуль разрешён". Что каждое новое
правило проверено не только на сниппетах, но и прогоном по корпусу. Что сроки не съедены
рефакторингом, не входящим в шаг.
